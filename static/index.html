          How to Use

          1. Organizations & Work Projects

          Work Projects live inside an Organization -- /<org-name>/<project-name>. Create an organization first (landing page, + New Organization), open it, then + Add Work Project inside it.

          2. Expected folder structure

          A "project folder" is any folder shaped like this — this dashboard scans for exactly this layout:

          your-project-folder/
├── modules/                          <- required, any content
├── tf-deployment-a/                  <- a "tf-deployment*" folder
│   ├── main.tf
│   ├── environmentVariables/
│   │   ├── terraform.dev.tfvars      <- defines env "dev"
│   │   └── terraform.prod.tfvars     <- defines env "prod"
│   └── backend/
│       ├── azurerm.dev.tfbackend     <- must match "dev"
│       └── azurerm.prod.tfbackend    <- must match "prod"
└── tf-deployment-b/                  <- another deployment, same shape

          An environment only shows up in the picker if the SAME name appears in both a terraform.<env>.tfvars file and an azurerm.<env>.tfbackend file — init needs the backend file, plan/apply need the tfvars file, so an environment missing either one can't actually be used. When adding a project you can either point at a folder already shaped like this ("Select existing folder"), or pick an empty folder and let the dashboard generate a minimal starter version of it for you ("Initialize new folder").

          3. Using the dashboard

          1. On the landing page, create or open an Organization.
          2. Inside it, click Add Work Project. Give it a name, then either Select existing folder (Browse + Scan Folder) or Initialize new folder (Browse to an empty folder + Initialize Folder).
          3. Pick which deployment and environment to use, then Create Project — this saves it and runs terraform init automatically. Init/Plan first check you're actually authenticated to the right cloud account (for Azure: logged in, and if the tfvars references a subscription_id, that it's one you can access) and fail with a clear message instead of a confusing terraform error if not.
          4. Open the project card. Click Run Plan (name it something) and watch the live output.
          5. Click Request Apply — this only shows you a summary and a one-time confirmation code. Nothing is applied yet.
          6. Type/paste that code and click Confirm & Apply to actually run terraform apply.
          7. Hover a project card and click ⋮ to edit its folder/deployment/ environment, clear its run history, or delete it (delete never touches real cloud resources — it only forgets the local bookkeeping entry). The same menu on an organization card deletes it and every project inside it.

          4. Using it from Claude Code (MCP)

          This dashboard doubles as an MCP server at http://127.0.0.1:8765/mcp. With the dashboard running, add it once to a project's .mcp.json:

          {
  "mcpServers": {
    "IaC-Dashboard": {
      "type": "http",
      "url": "http://127.0.0.1:8765/mcp"
    }
  }
}

          Restart Claude Code (or run /mcp) after the dashboard is running so it connects. Tools it gets:

          • list_organizations / add_organization / delete_organization — list, create, or remove (cascade) an organization
          • list_projects / discover_project / initialize_project_folder / add_project — list saved projects, scan an existing folder or scaffold a new one, save a new project
          • update_project / delete_project / clear_project_runs — edit, remove, or reset a saved project
          • init_project — run terraform init for a project (after checking cloud auth)
          • fmt / validate — local, no-cloud-calls checks; fmt reformats .tf/.tfvars files in place (recursively, so environmentVariables/ is covered)
          • terraform_plan / plan_destroy — run a named plan, or plan a full teardown
          • request_apply / confirm_apply — the same two-step confirmation as the UI; Claude always shows you the plan summary and waits for your yes before calling confirm_apply
          • get_run_status / list_runs — check progress

          Just ask in chat, e.g. "plan the QISP RAG sandbox project" or "add my other repo as a project and plan the prod environment" — Claude will call these tools itself, and any run it starts shows up in this same dashboard too.

          Add Work Project

          This organization's projects live in its repo -- creating this project will make a <name>/ folder there automatically, with a starter modules/ + tf-deployment/ (main.tf, backend/, environmentVariables/) inside it. It's committed and pushed as soon as you create it -- you'll still need to fill in real values (subscription id, resource group, etc.) in place of the REPLACE_ME placeholders before terraform init will work.

          Pick an EMPTY folder — this will create modules/ and a starter tf-deployment/ (main.tf, backend/, environmentVariables/) inside it, using the cloud provider selected above.

          Finished init/plan/apply runs older than this are deleted automatically (checked after every run and on server startup). Leave blank to keep run history forever.

          New Organization

Uses whatever git credentials already work on this machine; make sure it's a private repo, since real project data gets committed into it.
